# ADR-006: 数据开发模块架构决策

**Status**: Accepted  
**Date**: 2026-04-05

## Context

当前系统已具备数据源管理、元数据管理、数据服务与 ETL 编排能力，其中 ETL 侧已通过插件化执行器支持多执行后端（见 ADR-002）。随着数据团队使用场景扩展，需要引入数据开发模块，承接脚本研发与版本化管理能力，满足以下需求：

1. 多模式IDE： 支持 Web 端 SQL 编辑器、Python/PySpark 环境。提供统一的脚本研发入口，支持 SQL 与 Python 两类常见开发语言。
2. 支持脚本从草稿、保存版本到执行验证的完整闭环。
3. 与现有 ETL 执行能力协同，避免重复建设执行基础设施。
4. 首期以内部研发可用为目标，不引入复杂权限域和多租户隔离。

已有约束与参考：

- ETL 插件化执行架构（ADR-002）应保持稳定，不重复定义执行器体系。
- 模块化开发遵循现有 Django app 结构与后端规范（`docs/developments/creating-modules.md`、`docs/developments/backend-conventions.md`）。
- 重大功能设计需 ADR 记录，并同步任务与版本文档（`CLAUDE.md` 第 3.1 条）。

## Frontend Design 
参考 VS Code 或 Databricks
- 左侧：资源导航树 (Resource Explorer)
    目录树： 支持创建文件夹、SQL 文件。
    搜索框： 快速定位脚本名称。
    右键菜单： 新建、重命名、删除、移动。
- 中间：多页签编辑器 (Tabbed Editor)
    核心组件：可以使用已有sql编辑器或Monaco Editor（必须支持 SQL 语法高亮）。
    多页签管理： 同时打开多个脚本切换开发。
    工具栏：
    运行选中文档：即时查询。
    格式化 SQL：美化代码。
    保存：同步到后端数据库。
- 右侧/下方：辅助控制面板 (Panel)
  执行结果区： 展示 SQL 运行后的数据预览（表格形式）。
  日志区： 展示运行状态、耗时、报错信息。
  版本区：支持查看正式版本与草稿版本（可按全部/正式/草稿筛选）。
  任务配置区（侧边抽屉）： 配置调度周期、依赖关系、负责人等。

## Data Logic
- 脚本版本管理数据逻辑
  - 同一脚本可多次发布正式版本，形成可追溯的正式版本序列。
  - 同一脚本在任意时刻仅允许存在一个草稿版本。

## Decision

### 1. 模块定位

新增数据开发模块，定位为**脚本研发中心**，聚焦以下能力：

- 脚本资产管理（创建、编辑、删除、查询）
- 脚本版本管理（快照、版本回溯）
- 脚本执行触发与执行记录查询

本模块**不承担**任务调度编排职责；调度与依赖管理仍由既有 ETL 能力负责。

### 2. 复用策略

采用"**模型独立，执行层复用**"策略：

- 数据开发模块自建脚本域模型（Script、ScriptVersion、ScriptExecution）。
- 执行时通过适配层调用既有执行器能力（`apps.executors`），不复制执行器实现。
- 执行参数在脚本域与执行器接口之间做标准化映射，降低耦合。

### 3. 首期语言范围

首期支持两类脚本：

- SQL 脚本
- Python 脚本

其余语言（Spark SQL 文件化作业、Shell、R 等）不纳入首期范围，后续版本再评估。

### 6. 执行引擎策略补充（2026-04-06）

- 数据开发模块底层统一使用 **Spark SQL** 执行引擎。
- 新建脚本流程不再要求用户选择数据源，脚本执行默认提交到 Spark 执行。
- 版本历史视图需同时支持查看正式版本与草稿版本，避免草稿可见性缺失。

### 4. 权限与隔离策略（首期）

首期采用"**内部可用优先**"策略：

- 不引入项目级、多租户级细粒度权限模型。
- 沿用现有系统认证体系（SimpleJWT），保障基础访问控制。
- 为后续扩展预留字段边界（如 `owner`、`project_id`），但首期不强制实现。

### 5. 边界与非目标

以下能力明确排除在本 ADR 覆盖范围之外：

- DAG 调度、依赖编排与周期任务能力
- 实时协同编辑机制（OT/CRDT）
- 容器级沙箱执行与复杂资源隔离

## Consequences

**优点**:

- 复用既有执行器体系，建设成本低，交付路径短。
- 领域模型独立，避免与 ETL 任务模型强耦合，后续演进空间更大。
- 可快速形成"脚本研发 → 版本管理 → 执行验证"的最小闭环。

**缺点/风险**:

- 首期不做细粒度权限，内部协作场景下存在权限粒度偏粗的风险。
- 执行层复用依赖适配映射，若接口治理不足可能出现参数语义不一致。
- 仅支持 SQL/Python，部分高级开发场景需等待后续版本补齐。


## Follow-up

1. 形成详细技术设计（模型、API 清单、脚本状态机、错误码规范）。
2. 形成实施任务拆分并更新 `docs/requirements/active_tasks.md`。
3. 实施落地后更新 `docs/changelog.md`，标记对应版本条目。
4. 当引入项目级权限或多租户隔离时，补充后续 ADR（建议编号 ADR-007）。
