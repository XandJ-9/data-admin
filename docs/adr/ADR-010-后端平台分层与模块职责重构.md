# ADR-010: 后端平台分层与模块职责重构

**Status**: Accepted  
**Date**: 2026-04-22

## Context

随着 `datasource`、`dataintegration`、`datadev`、`dataasset`、`datatask` 多轮并行演进，当前后端已经出现以下结构性问题：

1. `datasource`、`dataasset`、`datatask` 的职责边界一度交叉，导致“采集入口、采集状态、采集落库”分散在多个应用中。
2. `datatask` 作为统一任务中心，曾直接通过 `source_module` 分支反向 import `dataintegration` / `datadev` 模型，逐渐侵入业务域。
3. 数据源连接上下文在多个应用内重复构建，密码解密、`params` JSON 解析、数据库覆盖等规则无法稳定保持一致。
4. `dataasset` 既承担资产语义沉淀，又承接兼容元数据模型，若继续让其主导流程入口，会进一步放大“资产域”和“流程域”混杂的问题。

`ADR-011-平台五阶段职责划分规范` 已明确完整链路分为 5 个阶段：

1. Connection & Discovery
2. Data Integration
3. Data Development
4. Orchestration & DataOps
5. Assetization & Service

因此需要把当前 Django 后端重新抽象为**业务入口层 + 平台内核层 + 资产治理层**，让每个应用在整个平台中拥有清晰、稳定、可扩展的角色。

## Decision

### 1. 采用“三个业务入口 + 一个平台内核 + 一个资产语义层”的结构

#### 业务入口层

- `apps.datasource`
- `apps.dataintegration`
- `apps.datadev`

这三个应用是用户直接感知的平台主流程模块，分别承接：

- **datasource**：连接与发现
- **dataintegration**：数据搬运入仓
- **datadev**：建模与加工开发

#### 平台内核层

- `apps.datatask`

该应用不再被视为普通业务模块，而是平台级运行内核，负责：

- 统一任务定义 `Task`
- 任务依赖 `TaskDependency`
- 运行实例 `TaskInstance`
- 调度状态、实例运维
- 任务来源分发协议

#### 资产治理层

- `apps.dataasset`

该应用作为资产与元数据的语义沉淀层，负责：

- 规范资产模型
- 兼容元数据模型
- 采集结果落库
- 资产双写同步
- 为血缘、标签、服务化提供稳定锚点

### 2. 明确五个核心应用的职责边界

#### `apps.datasource`

负责：

- `DataSource` 定义
- 数据源连接校验
- 探查与采集编排
- 统一 executor info 构建
- 源数据发现 API

不负责：

- 资产模型持久化细节
- 元数据兼容模型定义
- 统一任务调度内核

#### `apps.dataintegration`

负责：

- 贴源同步任务配置
- 源到目标的映射规则
- 入仓任务的业务语义
- 作为 `DATA_SYNC` 类型接入统一任务中心

不负责：

- 调度依赖拓扑内核
- 资产语义落库

#### `apps.datadev`

负责：

- 数据模型定义
- SQL / Python 作业
- 研发态治理卡点（表注释、字段注释、负责人等）
- 作为 `SQL_COMPUTE` 类型接入统一任务中心

不负责：

- 统一任务依赖调度规则
- 连接上下文构建规则重复实现

#### `apps.datatask`

负责：

- 平台级任务抽象与运行时
- 统一调度、实例、依赖、运维
- 任务来源注册与分发

不负责：

- 直接 import 业务应用模型并写业务逻辑
- 直接掌握来源模块的内部实现细节

#### `apps.dataasset`

负责：

- 资产主模型
- 兼容元数据模型
- 元数据采集结果落库
- 规范资产双写
- 后续资产地图、血缘、服务化的语义基础

不负责：

- 连接测试入口
- 统一任务调度内核
- 作为步骤 1 的主流程入口

### 3. 所有任务来源必须通过注册机制接入 `datatask`

`datatask` 不再通过 `if source_module == ...` 分支反向 import 业务模块模型，而是仅通过 registry 分发：

- `dataintegration` 通过 `task_source.py` 注册自己的 handler
- `datadev` 通过 `task_source.py` 注册自己的 handler
- 后续如 `datasource` 需要正式接入任务运维，也必须通过相同模式接入

注册 handler 负责：

- 业务配置模型 → `Task` 同步
- `Task` 回写来源业务模型
- `Task` 执行时的来源对象解析与执行分发

### 4. 所有连接上下文只能由 `datasource` 统一构建

新增统一连接上下文 helper，由 `apps.datasource` 负责：

- 解密已落库密码
- 解析 `params` JSON
- 应用数据库名覆盖

后续所有执行器调用必须统一复用该入口，包括：

- 数据源探查
- 数据服务查询
- 数据开发脚本执行

### 5. `dataasset` 通过 facade 暴露公开能力，不直接暴露内部实现给流程域

对于 `datasource -> dataasset` 这类跨域调用，只允许依赖：

- facade
- registry
- shared helper

不允许直接依赖 `dataasset` 的内部：

- `models.py` 细节
- `serializers.py` 细节
- `services.py` 细节

本阶段通过 `apps.dataasset.facades.metadata_collection` 暴露元数据采集任务与单表采集能力，作为兼容期的稳定边界。

### 6. `datasource` 暂不直接作为正式任务来源接入 `datatask`

当前 `MetaCollectionTask` 更接近“采集实例追踪”，而不是“可复用、可编排、可长期治理的任务定义”。

因此本 ADR 规定：

- **短期**：`datasource` 继续以业务入口方式承载探查与采集编排
- **中期**：若要将源数据采集纳入任务运维，需先新增“采集任务定义模型”
- **之后**：再通过注册机制接入 `datatask`

不得直接把一次性采集实例等价映射为平台级 `Task`。

## Consequences

**优点**:

- 平台层级更清晰，业务入口、运行内核、资产治理不再混杂。
- `datatask` 从“知道所有业务模块内部细节”的中枢，收敛回统一任务内核。
- `datasource`、`dataintegration`、`datadev` 可以持续迭代，而不再把变化扩散到 `datatask` 主体。
- `dataasset` 的角色从“流程入口候选”收敛为“语义沉淀中心”，更符合资产平台演进方向。

**缺点 / 风险**:

- 兼容期内 `MetaCollectionTask` 仍保留在 `dataasset`，流程入口在 `datasource`，需要通过 facade 维持清晰边界。
- `datadev` 与 `dataintegration` 会新增 `task_source.py` 这层注册适配代码，短期心智成本略有上升。
- `datasource` 尚未正式进入统一任务运维，源数据采集的任务定义与实例语义仍待 Phase 2 补齐。

## Follow-up

### Phase 1（当前阶段）

1. 将 `datatask` 改为 source registry 分发。
2. 将连接上下文统一收敛到 `apps.datasource`。
3. 为 `dataasset` 暴露 facade，隔离 `datasource` 对其内部实现的依赖。
4. 完成第一轮文档、测试和边界收敛。

### Phase 2

1. 为 `datasource` 设计正式的“采集任务定义模型”。
2. 将源数据周期采集、范围模板、任务策略接入 `datatask`。
3. 让 `TaskInstance` 与源数据采集实例语义对齐。

### Phase 3

1. 将 `dataasset` 从兼容模型并存逐步收敛到规范资产模型主导。
2. 在稳定任务链基础上引入标准血缘来源建模。
3. 将数据服务发布、资产服务化与资产血缘进一步联动。
