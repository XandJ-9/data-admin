# ADR-011: 平台五阶段职责划分规范

**Status**: Accepted  
**Date**: 2026-04-23

## Context

ADR-010 已明确当前平台采用“业务入口层 + 平台内核层 + 资产治理层”的后端分层结构，并将平台主链路抽象为 5 个阶段：

1. Connection & Discovery
2. Data Integration
3. Data Development
4. Orchestration & DataOps
5. Assetization & Service

但在实际需求讨论、模块设计与代码实现中，以上 5 个阶段仍容易出现以下混淆：

1. 把“连接与发现”阶段误写成资产语义阶段，导致流程入口与资产沉淀混杂。
2. 把“数据集成”与“数据开发”混用，导致贴源搬运和数仓建模边界不清。
3. 让“任务运维”反向掌握业务模块内部细节，导致平台内核侵入业务域。
4. 把“资产化与服务”退化成元数据展示页，无法成为统一的资产语义与对外服务出口。

因此需要新增一份面向后续所有开发的统一 ADR，正式固化这 5 个阶段的**目标、职责、非职责、交付物与越界约束**，作为后续需求拆分、模块设计、接口定义、页面组织与跨应用协作的统一规范。

## Decision

### 1. 五阶段采用“前一阶段产出标准化输入，后一阶段负责消费与深化”的链式职责模型

平台主链路必须按以下顺序理解与设计：

1. **Connection & Discovery**：解决“源头在哪里、如何连接、源端长什么样”。
2. **Data Integration**：解决“源数据如何稳定进入平台或数仓”。
3. **Data Development**：解决“进入平台后的数据如何建模、加工、产出可复用结果”。
4. **Orchestration & DataOps**：解决“集成与开发产物如何长期稳定运行、调度、监控与运维”。
5. **Assetization & Service**：解决“加工结果如何沉淀为可理解、可治理、可搜索、可服务化的资产”。

任一阶段都不得长期替代前置阶段补基础能力，也不得越界吞并后置阶段的独立职责。

### 2. 明确五阶段的标准职责边界

#### 2.1 Connection & Discovery

目标：建立可信连接并完成源端发现。

负责：

- 数据源定义、认证、连通性校验。
- 统一连接上下文构建，包括密码解密、参数解析、数据库覆盖。
- 源库、表、字段等对象的探查与发现。
- 源数据采集编排入口。
- 为后续阶段提供稳定的源端元信息输入。

不负责：

- 资产语义模型定义与长期沉淀。
- 贴源同步后的入仓语义。
- 数仓建模、加工开发。
- 统一任务调度内核。

交付物：

- 可用的数据源连接。
- 标准化的连接上下文。
- 可消费的源端库表字段清单。
- 原始元数据采集结果。

当前模块归属：`apps.datasource`。

#### 2.2 Data Integration

目标：将源数据稳定搬运进入平台。

负责：

- 贴源同步任务配置。
- 源到目标的映射规则、加载策略、写入方式。
- 入仓任务业务语义。
- 以 `DATA_SYNC` 类型接入统一任务中心。

不负责：

- 数仓分层建模与分析加工。
- 统一调度依赖拓扑内核。
- 资产语义沉淀。

交付物：

- 已进入目标存储的贴源数据。
- 可复用的数据同步任务配置。
- 入仓执行记录与运行结果。

当前模块归属：`apps.dataintegration`。

#### 2.3 Data Development

目标：将入仓数据加工为可复用的数据模型与作业成果。

负责：

- 数据模型定义。
- SQL / Python 作业开发。
- 数仓分层加工与指标、主题、宽表等产物建设。
- 研发态治理卡点，例如表注释、字段注释、负责人等。
- 以 `SQL_COMPUTE` 等类型接入统一任务中心。

不负责：

- 源端连接探查。
- 贴源同步语义。
- 统一调度规则本身。
- 资产服务化出口定义。

交付物：

- 可版本化的数据模型。
- 可执行的数据开发作业。
- 满足最小治理约束的加工结果。
- 可发布到任务运维的任务定义。

当前模块归属：`apps.datadev`。

#### 2.4 Orchestration & DataOps

目标：承载平台级任务运行时，保障任务长期稳定运行。

负责：

- 统一任务定义、依赖、实例与运行时抽象。
- Cron 调度、依赖触发、失败重试、实例运维。
- 任务来源注册与统一分发。
- 运行态监控、执行记录、运维视图。

不负责：

- 直接持有业务模块内部实现细节。
- 直接定义数据集成或数据开发的业务配置语义。
- 资产模型定义与服务化语义。

交付物：

- `Task / TaskDependency / TaskInstance` 统一运行模型。
- 可调度、可观测、可追踪的任务体系。
- 平台级任务运维能力。

当前模块归属：`apps.datatask`。

#### 2.5 Assetization & Service

目标：将数据对象沉淀为可理解、可治理、可服务化的资产。

负责：

- 资产主模型与兼容元数据模型沉淀。
- 资产分类、主题域、业务域、生命周期、负责人、安全等级等语义维护。
- 血缘、标签、标准编码、资产地图等语义基础能力。
- 面向搜索、目录、发布、接口封装等服务化输出提供稳定锚点。

不负责：

- 源端探查入口。
- 入仓执行编排。
- 数仓开发作业本身。
- 统一任务调度内核。

交付物：

- 可检索的数据资产目录。
- 带业务语义和治理语义的资产对象。
- 可对外服务化的数据资产锚点。

当前模块归属：`apps.dataasset`。

### 3. 后续所有开发必须遵守以下阶段性约束

#### 3.1 阶段归属优先于模块便利

如果某项需求属于某一阶段的天然职责，即便其他模块当前实现更方便，也不得因此长期把责任放错层。短期兼容可以存在，但必须在设计中标注真实归属与后续收敛方向。

#### 3.2 前置阶段必须交付可被后续阶段直接消费的标准化输入

例如：

- Connection & Discovery 必须提供统一连接上下文与稳定源对象清单。
- Data Integration 必须产出明确的目标表与运行结果。
- Data Development 必须产出可纳入任务运维的作业定义。
- Assetization & Service 必须基于稳定资产锚点对外提供目录、搜索或服务化能力。

#### 3.3 平台内核不得侵入业务域

`datatask` 只能承载运行时与来源注册协议，不得通过反向 import 或分支判断掌握业务模块内部模型细节。

#### 3.4 资产层不得反向成为流程入口层

`dataasset` 是语义沉淀层，不得长期承担 Connection & Discovery 的主流程入口，也不得承担 Data Integration / Data Development 的业务编排职责。

#### 3.5 治理要求应优先嵌入阶段流程，而非额外造孤岛系统

例如注释、负责人、标准编码、质量校验、安全等级等要求，应尽量在建模、发布、服务化等关键节点内被机器校验，而不是只停留在文档或线下约束。

### 4. 该 ADR 作为后续需求评审与设计评审的强制检查项

后续任何涉及平台模块、页面、接口、任务、元数据、资产服务化的设计与实现，必须至少回答以下问题：

1. 该需求属于 5 个阶段中的哪一个主阶段？
2. 它的上游输入和下游交付物是什么？
3. 是否错误侵入了其他阶段的核心职责？
4. 是否引入了平台内核侵入业务域或资产层反向成为流程入口的问题？
5. 是否把必要治理约束嵌入到了正确阶段的流程中？

若无法回答以上问题，则不得视为完成架构设计。

## Consequences

**优点**:

- 平台 5 个阶段从“概念口号”升级为可执行的职责规范。
- 后续模块设计、接口定义和页面组织有了统一判断依据。
- 可以减少 Connection & Discovery、Data Integration、Data Development、Assetization 之间的职责漂移。
- 有助于把平台内核、业务入口、资产语义和治理要求持续维持在正确边界内。

**缺点 / 风险**:

- 短期会暴露历史实现中的阶段错位，需要逐步收敛，而不能一轮完成。
- 某些兼容期实现会同时出现“真实归属”和“暂存位置”不一致，增加文档与评审成本。
- 团队需要先适应“按阶段而非按文件归属思考”的方式，心智负担会暂时上升。

## Follow-up

1. 后续新增业务模块、任务来源、资产服务化能力时，必须显式标注所属阶段。
2. 涉及跨阶段改动的 ADR、需求文档与任务拆分，需要引用本 ADR 作为边界依据。
3. 后续如出现新的阶段职责漂移，应优先通过补充 ADR 或更新本 ADR 进行纠偏，而不是放任实现先行固化。
