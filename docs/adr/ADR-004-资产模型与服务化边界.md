# ADR-004: 资产模型与服务化边界

**状态**: Accepted  
**日期**: 2026-05-22

## 背景

平台需要把源端发现、数据开发产物和服务消费统一沉淀为可理解、可治理、可追溯的数据资产。旧元数据模型只表达表和字段，难以覆盖环境、catalog、schema、资产分类、生命周期、安全等级和服务化锚点。

同时，数据服务需要提供查询、接口、报表和导出能力，但不能绕开资产语义和 SQL 安全治理。

## 决策

### 规范资产模型

资产语义以以下模型为主：

- `AssetNamespace`
- `DataAsset`
- `DataAssetColumn`

它们负责表达：

- 数据源与环境。
- catalog / schema。
- 表、视图等资产对象。
- 字段、类型、业务术语、字段角色。
- 资产分类、数仓分层、生命周期、安全等级、负责人。

历史 `MetaTable`、`MetaColumn` 等模型只做兼容保留，不作为新功能主入口。

### 跨模块写资产必须通过 facade

跨模块写入资产时，默认通过 `dataasset.facades`。业务模块不直接写资产内部模型细节。

当前典型来源：

- `datasource` 采集源端元数据后写入资产。
- `datadev` 后续可将模型产物沉淀为资产。
- `dataservice` 可绑定资产作为服务化锚点。

### 数据服务是消费出口

`dataservice` 负责：

- 查询。
- 接口定义。
- 接口字段。
- 报表定义。
- 调用日志。
- 导入导出。

数据服务可以绑定 `DataAsset`，发布或执行接口时应校验接口数据源与资产所属数据源一致。

### SQL 安全治理

数据服务和开发查询默认只允许单条只读 SQL：

- SELECT
- WITH
- SHOW
- DESCRIBE
- EXPLAIN

普通查询和导出都必须设置最大行数限制。SQL 治理应尽量沉淀到后端执行层，前端校验只能作为辅助。

## 禁止事项

1. 让 `dataasset` 承担数据源连接、采集调度或数据同步编排。
2. 绕开 `dataasset.facades` 从其他模块直接写资产内部表。
3. 基于 legacy `meta-*` 模型扩展新主功能。
4. 在 `dataservice` 中允许写入型 SQL 或多语句 SQL。
5. 服务接口绑定资产时跳过数据源一致性校验。

## 影响

1. 资产层成为统一语义锚点。
2. 数据服务与资产目录能够建立可追溯关系。
3. 源端元数据、开发模型和服务接口不会各自形成孤立口径。
4. 资产治理能力可以围绕规范资产模型持续扩展。
