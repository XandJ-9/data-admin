# ADR-003: 统一任务内核与执行实例边界

**状态**: Accepted  
**日期**: 2026-05-22

## 背景

平台中存在多类可运行对象：源数据采集任务、数据集成任务、数据开发脚本任务。它们的业务配置不同，但调度、依赖、执行实例、运行状态和运维视图需要统一。

历史上曾出现过多个私有执行中心，例如数据源采集运行表、数据集成执行日志、数据开发脚本执行表。这会导致执行记录口径不一致、任务运维无法统一、业务模块和任务中心双写真源。

## 决策

### 业务模块保存正式任务定义

以下模型是当前正式业务任务定义：

- `datasource.DataSourceCollectionTask`
- `dataintegration.DataIntegrationTask`
- `datadev.DataDevScript`

`DataDevModel` 是模型定义，不是任务中心的任务来源。模型若需要长期调度，应生成或绑定 `DataDevScript` 后发布。

### `datatask.Task` 是平台镜像

`Task` 保存平台纳管所需字段：

- 任务类型。
- 来源模块。
- 来源记录 ID。
- 调度类型。
- Cron 表达式。
- owner。
- 平台状态。
- 发布快照 `task_config`。
- 最近运行状态。

`Task` 不是业务任务真源，不能代替来源模块的业务模型。

### `datatask.TaskInstance` 是唯一执行记录中心

所有正式任务执行记录统一进入 `TaskInstance`，包括：

- 数据源采集。
- 数据集成。
- 数据开发脚本。
- 定时调度。
- 依赖触发。
- 手动执行。

业务模块如果需要展示执行记录，只能基于 `TaskInstance` 查询和投影，不新增第二套正式执行历史表。

### SourceHandler 是来源接入边界

`datatask` 通过 `source_module + source_record_id` 和 source handler / registry 分发来源能力。

来源 handler 负责：

1. 加载来源业务定义。
2. 同步平台任务镜像。
3. 构造发布快照。
4. 执行来源任务。
5. 返回统一结果 envelope。
6. 提供来源特定的实例纠偏或清理钩子。

执行返回结构统一为：

```json
{
  "ok": true,
  "msg": "success",
  "data": {}
}
```

来源异常或返回结构异常时，`TaskService.execute_task` 必须稳定降级为失败结果，而不是让任务中心接口 500。

### 发布快照优先于业务草稿

任务中心和调度器执行时，优先读取 `Task.task_config` 中的发布快照。

业务页面的调试执行可以读取当前业务配置，但不应自动污染已经发布的任务快照。保存业务配置和发布到任务中心是两个动作。

## 禁止事项

1. 在 `datasource`、`dataintegration`、`datadev` 中新增正式私有执行历史表。
2. 把完整业务配置迁入 `datatask.Task`。
3. 让 `datatask` 直接 import 来源模块内部执行函数并写分支判断。
4. 手动执行后自动把任务变成可调度任务。
5. 在任务详情或执行记录读取接口中执行失联恢复等写数据库动作。

## 影响

1. 平台任务运维使用统一实例中心。
2. 来源模块保留业务表达能力，不被平台抽象压平。
3. 开发时需要维护 source handler，但换来清晰的跨模块边界。
4. 发布、调试、调度的行为更可控。
