# ADR-012: 统一任务定义与执行实例边界规范

**Status**: Accepted  
**Date**: 2026-04-26

## Context

`ADR-010-后端平台分层与模块职责重构` 已明确：

- `datasource`、`dataintegration`、`datadev` 属于业务入口层
- `datatask` 属于平台运行内核层

`ADR-011-平台五阶段职责划分规范` 也已明确：

- `datasource` 负责 Connection & Discovery
- `dataintegration` 负责 Data Integration
- `datadev` 负责 Data Development
- `datatask` 负责 Orchestration & DataOps

但在具体实现中，关于“谁持有正式任务定义，谁持有执行实例”仍然容易反复漂移，主要表现为：

1. 业务模块把一次性运行记录长期保留为私有执行中心。
2. `datatask.Task` 被误当成业务任务真身，而不是平台镜像。
3. 平台任务运维希望统一查看所有执行记录，但业务模块又各自维护一套本地执行表。
4. 任务中心执行时，容易混淆“当前业务草稿”与“已发布任务快照”。

尤其在当前主干中，这个问题已经真实出现过：

- `datasource` 曾有 `DatabaseAssetSyncRun`
- `dataintegration` 曾有 `DataIntegrationExecutionLog`
- `datadev` 曾有 `DataDevScriptExecution`

如果不把这条规则单独固化，后续协同开发时仍会不断回到“双执行中心”或“平台模型侵入业务域”的旧路径。

## Decision

### 1. 三个业务模块各自保留“正式任务定义”

以下业务模块必须保留自己的正式任务定义模型：

- `datasource`
- `dataintegration`
- `datadev`

原因是三者的业务语义不同：

- `datasource` 关注采集范围、采集对象、采集策略
- `dataintegration` 关注源到目标的同步配置、加载方式、写入模式
- `datadev` 关注脚本、模型、版本、治理约束

因此**不得要求前端或业务逻辑直接把 `datatask.Task` 当成唯一业务配置模型使用**。

当前主干对应关系为：

- `datasource`：`DataSourceCollectionTask`
- `dataintegration`：`DataIntegrationTask`
- `datadev`：`DataDevScript` / `DataDevModel`

### 2. `datatask.Task` 是平台镜像，不是业务真身

`datatask.Task` 的职责是承载平台侧统一治理与编排信息，包括：

- `task_type`
- `schedule_type`
- `cron_expression`
- `owner`
- `task_config`
- 统一任务编码、统一任务状态、统一来源锚点

它是**业务任务定义映射到平台内核后的镜像**，不是来源业务模型本身。

因此：

1. 业务模块内部字段设计，优先由自身模型表达。
2. `Task` 只保存平台运行、调度、运维所需的公共抽象。
3. `Task.task_config` 中保存的是**平台执行快照**，不是业务模块任意草稿态的直接映射。

### 3. `datatask.TaskInstance` 是唯一执行记录中心

后续所有任务执行历史，统一只允许落到：

- `datatask.TaskInstance`

包括但不限于：

- 源数据采集执行
- 数据集成执行
- 数据开发脚本执行
- 数据模型建表执行
- 后续依赖触发、定时调度、失败重试实例

这意味着：

1. 业务模块不得长期保留第二套正式执行记录中心。
2. 业务模块若需要自己的详情视图，必须基于 `TaskInstance` 做查询和投影，而不是继续新增私有执行表。
3. 平台任务运维模块查看的“执行记录”，与业务模块查看的“执行记录”，底层必须是同一批实例数据。

### 4. 所有任务来源统一通过 source handler / registry 接入

`datatask` 不得通过反向分支判断掌握业务模块内部实现，而必须通过来源注册协议接入：

- `source_module`
- `source_record_id`
- source handler / registry

接入层负责：

1. 业务任务定义 → `Task` 平台镜像同步
2. 平台治理字段 → 业务任务定义必要回写
3. 平台执行 → 来源对象解析与执行分发
4. 执行记录展示前的来源特定纠偏、实例归一化或失联恢复，也必须通过 source handler 暴露，`datatask` 不得直接反向依赖业务模块内部实现

当前主干对应来源示例：

- `datasource.collection`
- `dataintegration.task`
- `datadev.script`
- `datadev.model`

### 5. 发布快照与调试草稿必须分离

统一任务中心执行时，必须优先使用已发布到 `Task.task_config` 中的快照，而不是直接读取来源业务模型的当前草稿。

因此：

1. **业务页面调试执行**，可以基于当前版本、当前配置、当前页面态运行。
2. **任务中心 / 调度器执行**，必须基于 `Task.task_config` 中的快照运行。
3. 未重新发布前，业务模块中的草稿变更不得自动污染已发布任务的执行快照。

### 6. 禁止新增业务模块私有执行中心

后续开发中，以下做法一律视为违背架构基线：

1. 在 `datasource`、`dataintegration`、`datadev` 中再次新增独立执行记录表，用作正式运行历史。
2. 用业务模块私有执行记录代替 `TaskInstance` 作为任务运维事实来源。
3. 让 `datatask` 直接持有业务模块内部模型细节，而不通过 registry 协议。

如果确有兼容期需要保留历史表，必须满足：

- 仅作为迁移过渡
- 明确标注真实归属仍是 `TaskInstance`
- 必须给出收敛删除路径

## Consequences

**优点**:

- 三个业务模块与 `datatask` 的边界变得清晰稳定。
- 平台任务运维终于可以统一查看所有执行历史，而不是跨模块拼接多套口径。
- 业务模块仍保有自己的领域配置能力，不会被平台抽象过度压平。
- “业务草稿”和“平台发布快照”分离后，调试与调度行为更可控。

**缺点 / 风险**:

- 需要额外维护一层来源适配代码（`task_source.py` / handler）。
- `Task` 与业务定义模型会并存，协作者需要理解“业务真身”和“平台镜像”的差异。
- 历史私有执行表迁移到 `TaskInstance` 时，需要谨慎处理时间线、结果摘要与旧数据回填。

## Supersedes / Clarifies

1. 本 ADR 细化并补充 `ADR-010` 中“业务入口层 vs 平台内核层”的任务边界。
2. 本 ADR 细化并补充 `ADR-011` 中“Orchestration & DataOps 不侵入业务域”的具体落地规则。
3. 本 ADR 替代 `ADR-008` 中关于 `DataDevScriptExecution` 可长期作为兼容执行日志并存的阶段性判断；当前主干正式基线已经收敛为 `TaskInstance` 单一执行中心。

## Follow-up

1. 后续新增任何任务来源时，必须先回答：
   - 正式任务定义模型放在哪个业务模块？
   - `Task` 如何作为平台镜像？
   - `TaskInstance` 如何作为唯一执行实例中心？
2. 若某业务模块仍存在历史私有执行表，应优先规划回填迁移和删除路径。
3. 后续文档入口必须把本 ADR 与 `ADR-010`、`ADR-011` 一起列为协同开发优先阅读项。
