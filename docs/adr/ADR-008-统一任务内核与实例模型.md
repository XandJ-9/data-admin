# ADR-008: 统一任务内核与实例模型

**Status**: Partially Superseded  
**Date**: 2026-04-18

> 时效性说明（2026-05-16）：本 ADR 关于统一任务中心的引入背景仍有效；关于 `DataDevScriptExecution` 与 `TaskInstance` 长期兼容并存的阶段性判断已被 ADR-012 覆盖，当前主干以 `TaskInstance` 作为唯一正式执行记录中心。

## Context

以 `ADR-011-平台五阶段职责划分规范` 为当前目标态基线，平台需要以统一的 `Task / TaskDependency / TaskInstance` 为中轴，贯通：

1. 数据集成任务（DATA_SYNC）
2. 数据开发 SQL 任务（SQL_COMPUTE）
3. 依赖编排与实例运维

制定本 ADR 时的主干中：

- `dataasset` 仅有 `MetaCollectionTask`，只覆盖元数据采集。
- `datadev` 仅有 `DataDevScriptExecution`，属于脚本域局部执行日志。
- 仓库不存在统一任务定义、依赖关系与实例层模型。

如果继续按分散模型推进，将无法支撑后续的“数据搬运入仓 → SQL 开发 → DAG 编排 → 资产服务化”主链路。

## Decision

### 1. 新增 `apps.datatask` 作为统一任务中心

新增三个核心模型：

- `Task`：统一任务定义，承载 `task_type / task_config / schedule_type`
- `TaskDependency`：任务依赖边
- `TaskInstance`：任务运行实例

### 2. 先接入 `datadev`，不恢复旧 `dataetl`

首个接入方选择 `datadev`：

- `DataDevScript` 通过 `source_module='datadev.script' + source_record_id=<script_id>` 映射到统一 `Task`
- 每次脚本执行创建一条 `TaskInstance`
- 早期曾规划 `DataDevScriptExecution` 保留并关联到 `TaskInstance`；当前主干已完成收敛，正式执行记录统一进入 `TaskInstance`

旧 `dataetl` 模块已下线，因此后续“数据集成”能力应直接接入 `datatask`，而不是恢复旧模块。

### 3. 保持血缘后置，但提前预留任务来源锚点

本阶段仍不实现自动血缘，但 `Task.task_config` 中要求保存来源脚本/数据源/版本等关键锚点，为后续从任务链反推资产血缘预留基础。

## Consequences

**优点**:

- 统一了任务定义与实例层，为后续调度、重试、依赖关系和运维拓扑提供稳定中心。
- `datadev` 可以逐步从“孤立执行日志”演进为“平台标准任务”。
- 后续数据集成、调度器、资产自动血缘都能围绕同一任务域扩展。

**缺点 / 风险**:

- 初期曾存在 `MetaCollectionTask`、`DataDevScriptExecution` 与 `Task/TaskInstance` 并存；当前正式执行记录口径已由 ADR-012 收敛为 `TaskInstance` 单一中心。
- 制定本 ADR 时只接通 `datadev`；当前更多任务来源已按 ADR-012 接入 `datatask`。
- `task_config` 首期仍以 JSON 承载运行配置，字段治理需后续继续收敛。

## Follow-up

1. 数据集成、数据开发与数据源采集已按来源模块接入统一任务中心。
2. `TaskDependency` 已作为平台任务依赖模型保留，前端依赖编排继续按当前产品口径演进。
3. 自动血缘来源建模与资产联动仍以后续资产治理阶段为准。
