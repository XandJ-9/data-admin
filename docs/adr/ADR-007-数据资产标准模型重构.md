# ADR-007: 数据资产标准模型重构（Phase 1）

**Status**: Accepted  
**Date**: 2026-04-17

## Context

当前 `dataasset` 模块只有 `MetaTable`、`MetaColumn`、`MetaCollectionTask`、`TableLineage` 四类核心模型，能够支撑轻量级元数据采集与表级血缘维护，但存在以下问题：

1. 元数据模型只有“表 / 字段”两层，缺少 `environment / catalog / schema` 这一层级。
2. `MetaTable.database` 以单字段承载命名空间信息，无法稳定表达 PostgreSQL / Presto / Trino 一类多层命名空间。
3. 采集任务模型仅适合“整库采集 + 当前表进度”场景，缺少采集范围语义。
4. 若直接删除旧模型并切新接口，现有前端与采集逻辑会被整体打断。

用户已确认：

- 数据资产模块继续保留；
- 本轮先做**后端领域模型与迁移**；
- **先不要实现数据血缘功能重构**，血缘标准化留到后续阶段。

## Decision

### 1. 采用“新增规范模型 + 保留旧模型兼容”的迁移策略

本阶段不删除以下旧模型：

- `MetaTable`
- `MetaColumn`
- `TableLineage`
- `MetaCollectionTask`

而是在 `apps.dataasset` 中新增规范资产模型：

- `AssetNamespace`
- `DataAsset`
- `DataAssetColumn`

并扩展 `MetaCollectionTask` 的范围字段。

### 2. 首期规范化范围仅覆盖“源数据模型”

Phase 1 只落地以下后端模型能力：

- 命名空间标准化：`data_source + environment + catalog + schema`
- 资产主模型标准化：`DataAsset`
- 字段模型标准化：`DataAssetColumn`
- 采集任务范围标准化：`scope_level / scope_catalog_name / scope_schema_name / scope_asset_name / run_mode`

### 3. 血缘标准化明确后置

本阶段**不新增规范血缘模型**，也不对现有 `TableLineage` 做平台级重构。

原因：

- 用户明确要求“先不要实现数据血缘功能”；
- 相比血缘，命名空间与资产主模型是更基础的领域边界；
- 若先上血缘标准模型，会把问题范围扩大到字段级血缘、任务来源、关系方向语义和前端图谱兼容，超出当前阶段目标。

### 4. 采集链路采用“双写到规范资产模型”

在现有采集逻辑中保留旧模型写入，同时同步刷新：

- `AssetNamespace`
- `DataAsset`
- `DataAssetColumn`

保证新旧模型短期并存时数据不会立即漂移。

## Consequences

**优点**:

- 可以先把最核心的资产领域结构扶正，而不打断现有表/字段接口。
- 后续前端与 API 可逐步从旧模型切换到规范模型。
- 为未来的血缘、标签、负责人、资产状态、治理规则扩展留出稳定锚点。

**缺点 / 风险**:

- 新旧模型会短期并存，维护成本上升。
- `TableLineage` 仍保持旧设计，血缘能力暂时继续停留在历史模型。
- 当前 schema 信息仍受采集器能力约束；Phase 1 已补齐 Presto/Trino 的 `catalog.schema` 拆分，其余数据源仍允许 `schema_name=''`。

## Follow-up

1. Phase 2：将查询接口逐步切换到 `AssetNamespace / DataAsset / DataAssetColumn`。
2. Phase 3：单独设计血缘标准模型 ADR，再决定是否引入字段级血缘与关系来源。
3. 若后续要上治理属性（标签、负责人、生命周期、认证状态），在 `DataAsset` 周边继续扩展模型。
