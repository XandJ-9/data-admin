# datatask 模块专项评审稿（2026-04-29）

## 1. 评审背景

本稿只聚焦 `apps.datatask`，不再扩展到 `datasource`、`dataintegration`、`datadev` 的功能完备性评审。

本次评审基于以下已确认前提：

1. 业务模块才是正式任务定义的真源。
2. `datatask.TaskInstance` 是全平台唯一执行实例中心。
3. 只有显式发布到任务中心的任务，才应该进入 `datatask.Task` 的纳管与调度范围。
4. 手动执行可以统一进入 `TaskInstance`，但不应因为一次手动执行就自动变成调度任务。

评审依据：

1. `ADR-010-后端平台分层与模块职责重构`
2. `ADR-011-平台五阶段职责划分规范`
3. `ADR-012-统一任务定义与执行实例边界规范`
4. 当前主干中的 `apps.datatask` 代码实现

## 2. 结论摘要

当前 `datatask` 的方向是对的，但核心抽象仍偏向“平台镜像一份任务定义”，还没有完全收敛到“只管理已发布任务的调度索引与执行实例”。

更准确地说：

1. `TaskInstance` 作为统一执行中心的方向成立。
2. `source handler / registry` 作为来源模块接入边界的方向成立。
3. 当前 `Task` 模型仍承载了过多业务任务定义字段，与“业务模块是真源”的目标仍有张力。
4. 当前调度链已经验证出一个关键约束：`Task` 不能完全不保存调度判定信息，否则调度服务会退化为跨模块逐条回源扫描。

综合结论：

- **`Task` 不应继续保存完整任务定义。**
- **`Task` 也不应被削减为只有业务任务 ID 的空壳引用。**
- **更合理的目标是：`Task` 只保留已发布任务的最小纳管关系与调度索引，完整业务定义继续留在业务模块；若需要冻结发布版本，则额外承接发布快照。**

## 3. 当前实现中的主要问题

### 3.1 `Task` 当前仍偏向“任务镜像”而不是“发布登记”

当前 `Task` 模型包含 `task_code`、`name`、`description`、`schedule_type`、`cron_expression`、`task_config` 等字段，结构上仍像一份平台侧任务副本。

这会带来两个直接问题：

1. 业务任务定义与平台任务镜像形成双写语义。
2. `datatask` 容易反向承担“修改业务任务定义”的职责。

若继续保留这套结构，`datatask` 会持续处于“任务管理中心”和“业务任务副本仓库”之间的混合状态。

### 3.2 调度治理规则尚未完全收敛到单一领域入口

当前任务更新、调度字段恢复、依赖切换后的调度策略修正等逻辑分散在 View 与 Service 两层。

这说明 `datatask` 还没有形成一个足够清晰的“任务发布态治理服务”，导致：

1. 平台规则难以从单一入口审计。
2. 后续新增来源模块时，容易重复复制类似判定逻辑。
3. 调度字段与来源模块状态之间的关系仍更多依赖约定，而不是显式领域模型。

### 3.3 `SourceHandler` 协议方向正确，但类型契约仍偏弱

当前 registry 已经把 `datatask` 从直接依赖来源模块内部实现中拉出来，这是正确方向。

但 `SourceHandler` 的函数签名仍然偏宽，更多依赖 `Callable[..., Any]` 与 JSON 约定配合运行。这在短期内降低了接入门槛，但中长期会带来：

1. 协议可发现性弱。
2. 返回结构不稳定时只能靠运行时兜底。
3. 发布快照、运行时覆盖参数和来源模型之间的边界继续模糊。

## 4. 已明确的设计约束

### 4.1 `Task` 不能只存业务任务 ID

如果 `Task` 只保留 `source_module + source_record_id`，调度器每轮就必须跨业务模块实时读取每个任务的调度定义，才能判断哪些任务需要执行。

这种做法不合理，原因包括：

1. 调度周期会退化为 N+1 回源扫描，查询成本随任务量线性放大。
2. 调度内核会重新耦合各业务模块的任务定义结构。
3. “发布”会退化为登记动作，无法形成清晰的发布态边界。

因此，`Task` 即使不存完整任务定义，也必须保存足够支撑高效筛选的调度索引字段。

### 4.2 调度器需要“先粗筛，再精取”

更合理的运行链应分为两段：

1. 粗筛：只基于 `datatask` 自己的表，快速选出“已发布、启用、当前到点”的任务。
2. 精取：只对命中的任务，再去读取发布快照或来源模块定义，用于真正执行。

这个原则意味着 `datatask` 需要保存最小可筛选信息，而不是零信息或完整镜像两种极端之一。

## 5. 建议的目标模型

### 5.1 `Task` 目标职责

`Task` 应收敛为“已发布任务的纳管关系与调度索引”，建议只承载：

1. 任务来源标识：`source_module`、`source_record_id`
2. 发布态与启停态：`publish_status`、`is_active`、`published_at`
3. 调度筛选字段：`schedule_type`、`cron_expression`
4. 任务中心自有治理字段：创建人、更新时间、软删除标记等

不建议再把完整业务配置、执行参数、字段映射等继续塞进 `Task`。

### 5.2 `TaskInstance` 目标职责

`TaskInstance` 继续作为全平台统一执行记录中心，承接：

1. 手动执行实例
2. cron 调度实例
3. 依赖触发实例
4. 统一执行状态、结果摘要、失败信息、触发方式与运行人

这一层当前方向成立，不建议重新拆回来源模块私有执行表。

### 5.3 发布快照的建议处理

若平台希望保留“点击发布后，以发布时版本进入调度”的能力，则建议引入独立的发布快照承载层，例如：

1. `TaskRelease`
2. 或在 `Task` 之外单独维护 `published_snapshot`

这样可以避免把 `Task` 主表重新膨胀成完整业务任务副本，同时保留发布态冻结能力。

## 6. 后续重构建议

后续如果继续推进 `datatask` 收敛，建议优先顺序如下：

1. 先收窄 `Task` 的职责，明确它是“发布登记 + 调度索引”，不是“任务完整定义镜像”。
2. 再把任务发布、停用、调度字段变更等治理逻辑收敛到单一 service 入口，避免 View 继续直接拼装治理字段。
3. 最后再增强 `SourceHandler` 的类型契约，把“来源记录加载、发布快照构建、执行调度、实例归一化”收敛成更稳定的协议层。

## 7. 当前判断

本稿记录的是 **当前针对 `datatask` 的专项评审结论与建议方向**，并不表示这些结构性收敛已经在代码中全部完成。

当前主干的真实状态仍以：

1. `docs/requirements/active_tasks.md`
2. `docs/changelog.md`
3. `ADR-010` / `ADR-011` / `ADR-012`
