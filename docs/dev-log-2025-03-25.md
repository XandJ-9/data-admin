## 三、关键设计决策

### 3.1 任务详情页拆分策略

**问题**：`taskDetail.vue` 承载了全部 7 个 Tab 页的模板和逻辑，代码量达 940 行，维护困难。

**方案**：按 Tab 页拆分为 6 个独立子组件，放在 `etl/components/` 目录下。原始的 SQL 配置和字段映射合并为一个 DataMappingTab，通过 FlipCard 翻转切换。

**收益**：
- 容器组件降至 ~420 行，职责清晰
- 每个 Tab 组件独立可测试、可复用
- 新增 Tab 无需修改容器

### 3.2 数据源实时自省 vs 元数据表关联

**问题**：原设计要求源表必须是 MetaTable FK 关联，意味着用户必须先做一次元数据采集才能配置 ETL 任务。

**方案**：新增 `source_table_name`、`source_database_name` 直写字段，DatasourceTab 通过 `/dataasset/collection/databases|tables|columns` 接口实时获取数据库/表/字段信息，无需预先采集。

**权衡**：MetaTable FK 保留用于向后兼容，但新建任务优先使用直写字段。

### 3.3 统计数据改为后端聚合

**问题**：ETL 首页和执行日志页都通过 `pageSize: 1000/10000` 拉取全量数据后在前端 JS 中计算统计指标。数据量增长后性能不可接受。

**方案**：后端新增 `/statistics` 聚合接口，使用 Django ORM `Count`、`Avg`、`Q` 在数据库层完成统计。前端一次 API 调用即可获取所有统计指标。

## 四、执行日志页修复详情

`executionLogs.vue` 存在大量字段名与后端 `ETLExecutionLogSerializer` 不匹配的问题，逐项修复如下：

| 位置 | 旧值（错误） | 新值（正确） | 原因 |
|------|-------------|-------------|------|
| 表格 ID 列 | `prop="id"` | `prop="logId"` | 序列化器输出 `logId`（source='id'） |
| 读取/写入列 | `row.rowsRead` / `row.rowsWritten` | `row.totalRows` / `row.successRows` | 模型字段为 `total_rows` / `success_rows` |
| 耗时列 | `row.duration` | `row.durationSeconds` | 模型字段为 `duration_seconds` |
| 数据大小列 | `row.dataSize` | _(删除)_ | 模型中不存在此字段 |
| 进度列 | `row.progress` | _(删除)_ | 列表序列化器不包含进度数据 |
| 详情弹窗 | `currentDetail.id` | `currentDetail.logId` | 同上 |
| 详情弹窗 | `currentDetail.duration` | `currentDetail.durationSeconds` | 同上 |
| 详情弹窗 | `currentDetail.executionMode` | `currentDetail.triggerType` | 模型字段为 `trigger_type` |
| 详情弹窗 | `currentDetail.failedRecords` | `currentDetail.failedRows` | 模型字段为 `failed_rows` |
| DataX 配置 Tab | `currentDetail.datxConfig` | `currentDetail.executorParams`（显示为 JSON） | 改为展示执行参数 |
| 查看详情 | `row.taskId` 传入 | `row.logId` 传入 | detail 接口需要日志 PK |
| 取消按钮 | `row.id` 传入 | `row.logId` 传入 | cancel 接口需要日志 PK |
| loadStatistics | 拉 10000 条前端计算 | 调用 `/statistics` 接口 | 改为后端聚合 |
| 未使用函数 | `formatBytes()` | _(删除)_ | dataSize 列已移除 |

## 八、经验总结

1. **前端页面字段必须严格对齐后端序列化器输出** — 本次执行日志页有 12 处字段名不匹配，根因是前端编写时未参考序列化器定义。建议后续通过 OpenAPI Schema 自动生成 TypeScript 类型。

2. **统计计算应在数据库层完成** — 前端拉取全量数据做 `filter/reduce` 的方式在数据量大时不可接受，Django ORM 的 `aggregate` + `Count`/`Avg`/`Q` 是更优解。

3. **大组件拆分提升可维护性** — taskDetail.vue 从 940→420 行，每个 Tab 独立后更容易定位问题和迭代。

4. **模块拆分后的 import 路径需全局检查** — 之前 datasource 从 dataasset 拆分后，integration 模块仍引用旧路径 `@/api/data/source`，直到本次构建才暴露。
