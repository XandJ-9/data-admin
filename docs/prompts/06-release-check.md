# 交付检查提示词

适用场景：准备提交 commit、发 PR、合并前或交付给用户前，做最终一致性检查。

```text
请对本轮改动做交付前检查。

前置要求：
- 先应用 docs/prompts/01-project-rules.md 的固定规则。
- 如果还没有做代码评审，先应用 docs/prompts/05-review.md。
- 不要在检查阶段扩展新功能；只修复阻断交付的问题。

检查清单：
1. Git 状态
   - 当前分支是否符合主目标命名。
   - 工作区是否只包含本轮目标相关改动。
   - 是否混入无关文件、临时文件、构建产物或本地配置。
2. 范围一致
   - 改动是否只服务本轮唯一目标。
   - 是否存在未授权重构、视觉调整、文案扩展或额外功能。
3. 前后端一致
   - API 路径、字段名、状态码、错误信息是否一致。
   - 前端 API 封装、页面消费字段、后端 serializer/view 是否对齐。
4. 权限一致
   - 后端 permission_map 是否覆盖新增/修改 action。
   - 菜单 seed 中 perms 是否存在并语义正确。
   - 前端按钮或入口是否使用 v-hasPermi。
5. 模块边界一致
   - 是否符合 ADR-002 和 ADR-003。
   - Task、TaskInstance、source handler、executors、dbutils 边界是否清晰。
6. 数据一致
   - 软删除、唯一约束、迁移、历史数据兼容是否处理。
   - 是否避免 N+1 查询和无界列表查询。
7. 文档一致
   - docs/requirements/active_tasks.md 是否更新当前真实状态。
   - docs/changelog.md 是否新增本轮变更，且新记录在旧记录之前。
   - README、ADR、开发规范是否需要同步；如果不需要，说明原因。
8. 验证一致
   - 是否运行最小必要测试。
   - 后端改动是否跑相关 app 测试。
   - 前端改动是否跑构建或页面验证。
   - 未能运行的测试是否说明原因和剩余风险。

输出格式：

交付结论：
<通过 / 需要修复 / 阻止>

本轮目标：
<一句话>

改动范围：
<列出主要文件或模块>

验证结果：
<列出命令和结果>

文档同步：
<说明 active_tasks.md / changelog.md / 其他文档状态>

剩余风险：
<没有就写“未发现明确剩余风险”>

建议提交信息：
<type>(<scope>): <中文描述>
```

提交信息示例：

```text
fix(scope): 修复模型字段软删除后的详情投影
```

```text
docs(prompts): 新增自主开发提示词模板
```
