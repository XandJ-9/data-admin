# 开发顺序纠偏方案（2026-04-30）

## 1. 文档定位

本文用于回答当前项目未来 4 到 6 周内“先做什么、不做什么、按什么顺序收口”的问题。

它不是新的长期架构 ADR，也不是模块功能说明书，而是当前阶段的**开发优先级纠偏文档**。后续需求评审、任务拆分、代码评审与页面实现，默认都应先检查是否符合本文定义的主线顺序。

涉及 `datasource`、`dataintegration`、`datadev`、`datatask`、`executors`、`dbutils` 的具体职责与执行层边界，统一以 `docs/developments/module-responsibility-execution-guide.md` 为开发手册。

## 2. 问题判断

当前项目的主要问题，不是缺少模块，而是开发顺序长期没有围绕单一主线收口，导致：

1. 多个模块都进入了建设状态，但没有任何一个模块形成真正稳定的产品闭环。
2. 架构边界、历史兼容、前端补洞、运行链修复在同一阶段并行推进，主线频繁漂移。
3. 高阶能力如发布、快照、冻结版本过早进入讨论，挤占了基础纳管闭环的交付窗口。
4. 团队容易围绕“还能再补什么”推进，而不是围绕“当前模块是否已经闭环”推进。

## 3. 当前阶段唯一主目标

未来 4 到 6 周，当前开发最优先要解决的事情只有一个：

**先完成业务任务定义真源与统一任务运维纳管闭环。**

具体含义如下：

1. `datasource`、`dataintegration`、`datadev` 继续各自保留正式任务定义模型。
2. `datatask.Task` 只承担统一纳管台账、来源锚点、依赖与调度索引，不回退为业务任务真身。
3. `datatask.TaskInstance` 继续作为全平台唯一执行实例中心。
4. 所有任务执行、数据库查询、库表字段探查与引擎运行能力，统一通过 `apps.executors` / `apps.dbutils` 承接，业务模块不得自建第二套执行层。
5. `monitor` 只围绕 `Task` 与 `TaskInstance` 建立统一运行控制面。
6. `dataasset`、`dataservice` 在本轮只消费稳定产物，不反向抢占主流程定义权。

## 4. 当前阶段明确不作为主线的事项

未来 4 到 6 周，以下事项允许讨论，但不进入主线验收标准：

1. 统一发布中心重构。
2. 独立发布快照模型。
3. 冻结版本与环境迁移工作流。
4. 发布审批流与复杂回滚机制。
5. 全量资产治理体系一次性建设。
6. 完整告警平台与大而全监控中台。

这些能力不是不要，而是必须排在“任务定义真源 + 统一任务运维纳管”之后。

## 5. 开发顺序总览

未来 4 到 6 周按以下顺序推进：

1. 第 1 周：冻结主线范围，统一纳管口径。
2. 第 2 周：优先收口 `datasource` 与 `dataintegration`。
3. 第 3 到 4 周：完成 `datadev` 真源收口，并与 `datatask` 运行链对齐。
4. 第 5 周：补齐 `datatask` 与 `monitor` 的统一运维闭环。
5. 第 6 周：再推进 `dataasset` 与 `dataservice` 的下游衔接。

## 6. 分阶段方案

### 6.1 第 1 周：冻结主线范围与统一纳管口径

只做什么：

1. 明确未来 4 到 6 周只围绕“业务任务定义真源 + `TaskInstance` 统一纳管”推进。
2. 对 `datasource`、`dataintegration`、`datadev` 三个业务模块逐一确认正式任务定义模型、来源标识、与 `datatask` 的镜像关系。
3. 对 `datatask` 逐一确认当前必须保留的最小纳管字段、依赖字段、实例字段和来源协议。
4. 对 `system` 补齐当前主线所需的最小菜单、权限、角色、入口控制。
5. 把 `monitor`、`dataasset`、`dataservice` 标记为跟随主线消费的后置模块，而不是当前主线定义者。

不做什么：

1. 不新开发布中心、快照中心、冻结版本中心。
2. 不为 `datatask` 继续补业务真身字段。
3. 不在业务模块中直接引入数据库驱动或引擎执行逻辑。
4. 不启动与当前主线无关的视觉重做、导航重排和泛后台改造。
5. 不把 `monitor` 先做成独立大监控平台。

完成标志：

1. 团队能够清楚回答三个问题：谁是真源、谁是镜像、谁是实例中心。
2. 团队能够清楚回答执行层问题：任务级执行走 `executors`，数据库级查询与探查走 `dbutils`。
3. 文档层面已经明确当前最高优先级与非目标清单。
4. 新需求评审时，不再围绕发布、快照、冻结版本重新抢主线。

主要风险：

1. 现有兼容字段和历史概念会继续误导协作者把兼容实现当正式目标。
2. 若 system、monitor 的旧通用后台思路重新进入主线，会再次带偏范围。

### 6.2 第 2 周：优先收口 `datasource` 与 `dataintegration`

只做什么：

1. 让 `datasource` 稳定表达连接、发现、采集范围和采集策略，不再把采集定义外溢到其他模块。
2. 让 `dataintegration` 稳定表达同步任务、源目标映射、加载策略和执行入口，不再依赖其他模块表达自身业务语义。
3. 统一这两个模块的“业务配置 -> 任务纳管 -> 实例记录”链路，确保执行历史只进入 `TaskInstance`。
4. 收口数据源删除、失联、重绑、禁用等状态切换，避免把历史私有执行逻辑带回来。
5. 确认数据源发现、连接测试、集成执行全部通过 `dbutils` / `executors`，不在业务模块单独实现外部数据库连接。
6. 只修与纳管主线直接相关的页面回链、菜单高亮、详情跳转和最小权限问题。

不做什么：

1. 不恢复或扩展 `datasource` 的 snapshot、冻结采集版本和复杂模板体系。
2. 不把 `dataintegration` 的主线转成“发布工作流完善”。
3. 不在 `datasource` / `dataintegration` 中新增私有执行器、私有数据库连接或私有执行历史。
4. 不优先做复杂执行器扩展、复杂依赖编排 UI 或大范围引擎抽象。
5. 不先推进 `dataasset` 资产语义精修和 `dataservice` 服务化包装。

完成标志：

1. `datasource.collection` 与 `dataintegration.task` 的业务配置、任务纳管、执行实例三层关系稳定。
2. 这两个模块的手动执行、任务中心查看、执行记录查看统一落在 `TaskInstance` 口径。
3. 数据库探查统一走 `dbutils`，集成任务执行统一走 `executors`。
4. 相关核心状态切换不会再重新制造第二套运行事实来源。

主要风险：

1. `datasource` 与 `dataintegration` 交界最容易发生“发现逻辑”和“同步语义”重新缠绕。
2. 若为了短期方便继续在 `datatask` 增补业务字段，会重新制造双写语义。

### 6.3 第 3 到 4 周：完成 `datadev` 真源收口并与 `datatask` 对齐

只做什么：

1. 让 `datadev` 继续承载脚本、模型、目录与研发态治理信息，不把这些信息迁回 `datatask`。
2. 统一 `datadev` 的调试执行、正式执行、任务纳管、实例查询链路，确保不再出现私有执行历史回流。
3. 收口 `datadev` 与 `datatask` 的接缝：`datadev` 负责定义与运行入口，`datatask` 负责纳管、依赖、实例与统一运维入口。
4. 确认 SQL 查询统一走 `dbutils`，Spark/Hive/MVP/建模类执行统一走 `executors`。
5. 仅建立最小的“加工结果可被资产层识别”能力，不提前把资产治理做深做重。
6. 对 `system` 补齐 `datadev` 所需的权限颗粒度、菜单入口和详情回链。

不做什么：

1. 不把当前主线切换成版本中心、发布审批、冻结版本重构。
2. 不优先做复杂环境迁移、发布回滚和多环境治理。
3. 不在 `datadev` 中新增绕开 `executors/dbutils` 的执行分支。
4. 不先做高级 IDE 化体验和在线终端体系扩张。
5. 不把字段级血缘、全量质量规则一次性压进本阶段。

完成标志：

1. `datadev` 的正式任务定义与运行历史边界清晰，不再依赖私有执行表或私有执行中心。
2. `datadev` 产物能被任务中心统一查看、统一触发、统一回溯。
3. 研发态操作与运维态查看共享同一批实例事实，不再出现两套执行结果。
4. 所有数据库查询、任务执行和建模执行均可追溯到 `dbutils` 或 `executors`。

主要风险：

1. `datadev` 复杂度最高，最容易把“开发态草稿”和“平台运行态”重新混成一套。
2. 若此阶段引入过多版本治理诉求，会直接偏离当前主线。

### 6.4 第 5 周：强化 `datatask` 与 `monitor` 的统一运维闭环

只做什么：

1. 在三个业务真源稳定后，集中强化 `datatask` 的统一台账、统一实例、统一来源查询、统一失败归因。
2. 让 `monitor` 基于 `Task` 与 `TaskInstance` 建立统一运行视图，只做运行态观察、异常归因、重试入口和基础告警口径。
3. 统一任务对象页、实例页、来源页之间的跳转与检索口径。
4. 只补当前主线所需的最小统计指标和状态看板。

不做什么：

1. 不先做完整 SLA 平台、告警编排中心、多渠道通知中台。
2. 不把 `monitor` 做成脱离 `datatask` 的第二调度系统。
3. 不为了监控展示重新长出各业务模块私有日志汇总表。
4. 不先处理与当前主线无关的旧 monitor 遗留泛化能力。

完成标志：

1. 运维人员可以基于统一任务对象和统一实例中心完成查看、定位、重试与追溯。
2. `monitor` 展示的运行事实与业务模块详情页看到的是同一套实例数据。
3. “业务定义真源在业务模块，运行事实真源在 `TaskInstance`”在页面和接口层都成立。

主要风险：

1. 现有 monitor 中若混入旧后台监控残留概念，会造成模型再次歧义。
2. 如果 `Task` 主表继续承载过多业务字段，`monitor` 也会被迫理解业务内部细节。

### 6.5 第 6 周：让 `dataasset` 与 `dataservice` 在稳定主线上消费成果

只做什么：

1. 在前四个阶段稳定后，再补 `dataasset` 与 `dataservice` 的承接能力，而不是让它们反向定义流程。
2. `dataasset` 只围绕稳定入仓结果、加工结果和资产锚点做沉淀，确保能识别来自 `datasource`、`dataintegration`、`datadev` 的稳定对象。
3. `dataservice` 只围绕稳定资产或稳定结果集建设查询、接口、报表等消费出口，不把自己变成任务定义入口。
4. `system` 只同步补齐资产、服务的访问控制与菜单组织。
5. `monitor` 只补与资产消费、服务调用关联的最小观察视角。

不做什么：

1. 不先做复杂资产标准体系、全量血缘体系、全量质量规则中心。
2. 不先做数据服务市场、审批流、发布版本矩阵。
3. 不把 `dataservice` 的服务发布流程抬升为当前阶段主线。
4. 不以“资产看起来更完整”为理由回头修改前三个业务模块的真源边界。

完成标志：

1. `dataasset` 已成为稳定产物的语义锚点，而不是流程入口替代者。
2. `dataservice` 已成为稳定产物的消费出口，而不是业务定义真源。
3. 上游任务定义、运行实例、下游资产服务三者之间的链路清晰可追溯。

主要风险：

1. 若上游真源和实例口径还未稳定，过早推进资产与服务会再次出现“下游倒逼上游改模”。
2. 资产、服务天然容易引入更多治理和展示诉求，存在再次扩 scope 的风险。

## 7. 模块优先级

第一优先级：

1. `datasource`
2. `dataintegration`
3. `datadev`
4. `datatask`

第二优先级：

1. `monitor`
2. `system`

第三优先级：

1. `dataasset`
2. `dataservice`

## 8. 当前阶段验收口径

1. 是否还能明确说出 `datasource`、`dataintegration`、`datadev` 各自的正式任务定义模型是什么。
2. 是否还能明确说出 `datatask` 只是平台纳管镜像，而不是业务真身。
3. 是否全平台执行历史都继续统一进入 `TaskInstance`。
4. 是否所有任务执行、数据库查询、库表字段探查都继续统一通过 `executors/dbutils`。
5. 是否 `monitor` 看到的运行事实与业务模块详情页看到的是同一批实例。
6. 是否 `dataasset`、`dataservice` 只消费稳定产物，没有反向抢占流程入口。
7. 是否没有把发布、快照、冻结版本重新拉回当前 4 到 6 周的主线。

## 9. 一句话结论

当前项目未来 4 到 6 周最重要的，不是再补更多能力点，而是强制把开发顺序压回“**业务任务定义真源 -> 统一任务纳管 -> 统一任务运维 -> 下游资产与服务消费**”这条单主线，并把所有不属于这条主线的事项暂时后置。
